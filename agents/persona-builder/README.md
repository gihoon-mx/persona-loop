# persona-builder (M05)

**응답자 한 사람이 문항 전체에 어떻게 답했는가**를 읽어 페르소나를 만든다. 문항별 집계에서 만들지 않는다.

> 집계("35명 중 71%가 X를 골랐다")는 통계 요약이지 사람이 아니다. X를 고른 71%와 Y를 고른 64%를 동시에 만족하는 응답자가 실제로는 한 명도 없을 수 있고, 그렇게 만든 페르소나는 **존재하지 않는 사람**이다. 존재하지 않는 사람은 유사 서비스 앞에서 어떻게 행동할지도 대변할 수 없다.
> 그래서 페르소나의 단위는 응답자 개인이고, 집계는 "이 사람이 다수인지 소수인지"를 알려주는 보조 정보로만 쓴다. (ARCHITECTURE.md §5)

출력 스키마: [`packages/core/schemas/persona.schema.json`](../../packages/core/schemas/persona.schema.json) — **이 문서보다 스키마가 우선**이다.

---

## 1. 입력

입력은 **집계가 아니라 응답자별 프로필**이다. 원천 데이터는 Firestore `projects/{pid}/surveys/{sid}/responses/{rid}` — **문서 1건 = 응답자 1명의 전체 답변**(`{answers:{qid:값}, submittedAt, source, respondentLabel}`)이며, 응답자 단위 데이터는 이미 있다. 화면이 문항별로만 접고 있었을 뿐이다.

에이전트에는 서베이 결과 화면(M03)이 내보낸 파일을 그대로 넘긴다(§6).

**본체 — `<sid>-profiles.json`** (응답자별 보기 → `전체 프로필 JSON`). `profiles[]`의 각 원소가 곧 `persona.schema.json`의 `answerProfile` 형태다.

```json
{
  "surveyId": "sv-2026-01",
  "surveyTitle": "동네 서비스 이용 설문",
  "exportedAt": "2026-07-25T04:10:00.000Z",
  "questionCount": 40,
  "respondentCount": 35,
  "profiles": [
    {
      "surveyId": "sv-2026-01",
      "respondentLabel": "P7",
      "answers": [
        { "questionId": "q3", "questionText": "낯선 동네에 갈 때 먼저 하는 일은?",
          "answer": "지도 앱을 켠다",
          "comment": "일단 내 위치부터 찍어봐요. 그래야 감이 와서요." },
        { "questionId": "q4", "questionText": "주로 쓰는 서비스는? (복수)", "answer": ["A", "C"] },
        { "questionId": "q5", "questionText": "…", "answer": null }
      ]
    }
  ]
}
```

**보조(권장) — `<sid>.json`** (문항별 보기 → `집계 JSON 내보내기`). 문항 정의(`type`·`options`·**`personaDimension`**)와 집계가 들어 있다. 문항 차원은 단계 2의 묶음 기준을 정확하게 만들고, 집계는 `populationContext`(다수/소수 표시)에만 쓴다 — **특성의 근거로는 쓰지 않는다.**

읽을 때 주의할 점:

- **무응답은 `answer: null`로 들어온다.** 빠뜨린 게 아니라 신호다(단계 1).
- **자유 의견은 원 문항의 `comment`로 접혀 있다.** 연동 서베이는 문항별 의견을 `<qid>-c` 주관식 문항으로 저장하는데, 내보내기가 이를 원 문항 행에 합친다. 따라서 의견을 인용할 때 `evidence.questionId`는 **원 문항 id(`q3`)** 를 쓴다. 원 문항이 사라져 `-c`만 독립 행으로 남은 경우에만 `q3-c`를 쓴다.
- **`respondentLabel`이 `응답 #3`일 수 있다.** 연동(now-here-survey) 응답은 `P1`·`P2`…지만 CSV 임포트·공개 폼 응답은 라벨이 없어 순번이 붙는다(정렬 고정 — 같은 데이터를 다시 내보내도 같은 번호). 페르소나 문서에도 **내보낸 라벨을 그대로** 쓴다. 임의로 다시 매기지 않는다.
- **실명은 입력에 없다.** 연동 단계에서 이미 제거됐다(`respondent: null`). 페르소나에도 라벨 외의 식별자를 만들지 않는다.
- 응답자가 35명이면 35명분 답변이 전부 컨텍스트에 들어간다. 비용은 응답자 수에 비례한다(§5).

## 2. 방법

### 단계 1 — 응답자별 프로필 구성

응답 문서 하나를 사람 한 명으로 펼친다. 문항 순서대로 `{questionId, questionText, answer, comment}`를 늘어놓으면 그것이 그 사람의 프로필이다.

- **무응답도 기록한다.** 지우지 말고 `answer: null`로 남기고 `readAs`에 "무응답 — 관심 밖이거나 답하기 곤란했던 문항"처럼 읽은 방식을 적는다.
- 무응답의 **모양**을 본다: 뒷부분을 통째로 비운 사람(중도 이탈)과 특정 주제만 비운 사람(회피)은 다른 사람이다. 자유 의견만 전부 빈 사람은 "말수 적음"이라는 `voice` 신호다.
- `answeredRatio` = 답한 문항 수 / 전체 문항 수. 나중에 `confidence`와 primary 선정에 쓴다.

### 단계 2 — 패턴이 닮은 사람끼리 묶기

**무엇으로 묶는가**

1. **핵심 문항의 답 조합** — `personaDimension`이 `goals`·`painPoints`·`behavior`·`attitude`인 문항들. 이 조합이 같은 방향이면 같은 묶음 후보다.
2. **자유 의견의 주제** — 무엇을 문제 삼는지, 무엇을 좋다고 하는지. 같은 선택지를 골랐어도 이유가 다르면 다른 사람이다. 이유가 묶음을 가른다.
3. (약한 신호) **무응답 패턴** — 같은 영역을 함께 건너뛴 사람들은 관심사가 닮았을 수 있다.

**묶지 말아야 할 것**

- 나이·성별·지역 같은 **인구통계만으로 묶지 않는다.** "30대 여성"은 행동을 예측하지 못한다. demographics 문항은 묶는 기준이 아니라 묶은 뒤 사람을 서술할 때만 쓴다.
- 응답 수를 맞추려고 억지로 묶지 않는다.

**묶음 수**: 응답자 30~40명이면 보통 3~5개. 어느 묶음에도 붙지 않는 **1명짜리 이상치는 버리지 않는다** — `basis: "individual"`, `clusterSize: 1`로 세우고 `populationNote`에 "35명 중 1명"이라고 밝힌다. 소수 의견이 제품 결정에 가장 쓸모 있는 경우가 많다.

### 단계 3 — 묶음마다 중심 응답자(primary) 한 명을 고른다

`basis`가 `cluster`여도 페르소나는 **한 사람을 기준으로 쓴다.** 여러 명의 답을 평균 내면 다시 집계 페르소나가 된다.

선정 기준(충돌하면 이 순서):

1. 자유 의견이 풍부하고 구체적인 사람 — 말투(`voice`)와 행동 모델의 재료가 여기서 나온다
2. `answeredRatio`가 높은 사람
3. 그 묶음의 전형적인 답 조합에 가장 가까운 사람

`sourceRespondents`에 primary 1명(`role: "primary"`)과 나머지(`role: "supporting"`)를 모두 적는다.
`answerProfile`에는 **primary 한 사람의 답변만** 담는다. supporting 응답자의 답은 `evidence`로 인용해 "혼자만의 이야기가 아님"을 보인다.

### 단계 4 — traits · goals · painPoints 도출

전부 `evidencedItem`이다. `evidence[]`에는 `{surveyId, questionId, respondentLabel, quote}`가 들어가고 **`respondentLabel`은 필수**다.

- `quote`는 그 사람이 **실제로 고른 선택지 값 또는 자유 의견 원문 그대로**. 요약·윤문·맞춤법 교정 금지.
- `populationContext`는 선택이다. 붙일 때도 "이 답이 흔한지 드문지"만 적는다("35명 중 6명"). 이것이 근거의 본체가 되면 안 된다.
- `demographics`는 응답에서 확인된 항목만 채우고, 나머지는 **비워 둔다.**

| | 예시 |
|---|---|
| ✅ 좋음 | `text`: "새 서비스를 열면 설명을 읽지 않고 바로 만져본다" / `evidence`: `{questionId:"q3", respondentLabel:"P7", quote:"일단 내 위치부터 찍어봐요. 그래야 감이 와서요."}` |
| ❌ 나쁨 | `text`: "탐색적 성향이 강하다" / `evidence`: `{questionId:"q3", quote:"71%가 '지도 앱을 켠다'를 선택"}` — 누구의 답인지 없고, 개인이 아니라 집계다 |

### 단계 5 — behaviorModel 도출 (이 모듈의 핵심)

**"이 사람이 유사 서비스를 처음 만나면 무엇을 하는가"**를 응답에서 읽어낸다. demo-reviewer(M07)가 이 규칙을 그대로 실행하므로, 지어낸 항목 하나가 곧 가짜 리뷰 한 편이 된다.

| 필드 | 어떤 답에서 읽어내나 | 예시 (가상) |
|------|----------------------|-------------|
| `firstMoves` | 기존 유사 서비스 이용 습관, "먼저 하는 일" 문항, 정보 탐색 방식, 자유 의견의 "저는 보통 ~부터 봐요" | P7이 q3에 "지도 앱을 켠다" + "일단 내 위치부터 찍어봐요" → **"홈에서 지도부터 열어 현재 위치를 확인한다"** |
| `decisionDrivers` | 중요도·선택 이유·만족/불만 이유 문항 | q11 "가장 중요한 것: 정보가 최신인지" → **"정보가 최근 것인지로 신뢰를 판단한다"** |
| `dealBreakers` | 그만둔 경험, 짜증 요인, 거부 조건 문항 | q18 "가입을 요구하면 그냥 나간다" → **"둘러보기 전에 가입·로그인을 요구하면 즉시 이탈"** |
| `successMoment` | "언제 만족했나", "쓸모 있었던 순간" 문항 | **"내가 아는 동네가 화면에 정확히 그려진 걸 본 순간"** |
| `comparisonAnchors` | 현재 쓰는 서비스·대안 문항 | 응답에 등장한 이름만 그대로. 응답에 없는 서비스를 넣지 않는다 |
| `effortTolerance` | 원하는 걸 못 찾을 때의 행동, 자유 의견의 참을성 표현 | "두세 번 눌러보고 안 되면 닫아요" → `low` |
| `helpSeeking` | 도움말·문의·주변에 묻기 관련 답 | "도움말은 안 봐요" → `never` |

지킬 것:

- **`painPoint`와 `dealBreaker`를 구분한다.** 불평이 많아도 계속 쓰고 있다면 그건 painPoint지 dealBreaker가 아니다. dealBreaker는 "그 자리에서 그만둔다"는 진술이 있을 때만 쓴다.
- 행동은 **기능 수준**으로 쓴다("경계를 확인할 방법을 찾는다"). 데모의 특정 버튼 이름·화면 구조를 전제하지 않는다 — 에이전트는 그 화면을 보지 않고 만들어졌다.
- `firstMoves`·`decisionDrivers`·`dealBreakers`는 스키마상 최소 1개다. 근거가 정말 없으면 **없는 대로 두지 말고 primary를 다른 사람으로 바꾸거나**, 불가피하면 `confidence.level: "low"` + `gaps`에 "dealBreaker는 직접 진술이 없어 이탈 경험 문항에서 추론" 처럼 명시한다.
- `effortTolerance`·`helpSeeking`은 근거가 없으면 `mid`/`rarely`로 두고 반드시 `gaps`에 적는다.

### 단계 6 — 모순 기록 · 신뢰도 산정

- `answerProfile.contradictions`: 서로 어긋나는 답을 **찾아서 적는다.** 예: "q12에서 '위치 공유가 꺼려진다'고 했으면서 q21에서는 '주변 추천이 가장 유용하다'를 골랐다."
  매끈하게 다듬으려고 지우지 않는다. 실제 사람은 일관적이지 않고, 이 긴장이 demo-reviewer의 행동을 진짜처럼 만든다(말로는 A라 했지만 실제로는 B를 누른다).
- `confidence`:

  | level | 기준 |
  |-------|------|
  | `high` | `answeredRatio` ≥ 0.8 · 자유 의견 3건 이상 · behaviorModel 전 항목에 직접 근거 |
  | `mid` | `answeredRatio` ≥ 0.5 · 자유 의견 1건 이상 |
  | `low` | 그 밖 (무응답 절반 이상이거나 자유 의견 0건) |

  `low`라고 페르소나를 버리지 않는다. **낮다고 표시**하고, 무엇을 추론으로 메웠는지 `gaps`에 남긴다.

## 3. 금지 사항

1. **집계 수치만으로 특성을 만들지 않는다.** "71%가 X라고 답함"은 근거가 아니다. 근거는 언제나 "누구의, 어떤 문항의, 어떤 답"이다.
2. **응답에 없는 인구통계를 추측으로 채우지 않는다.** 나이·직업·거주지·가구 구성은 물어본 것만 쓴다. 이름은 가명이며 그 자체로 속성을 만들지 않는다.
3. **모순을 지우지 않는다.** 페르소나를 매끄럽게 만들려고 어긋난 답을 빼면 남는 것은 평균값 인형이다.
4. **인용을 다듬지 않는다.** 오탈자·구어체·비문 그대로 옮긴다. 다듬는 순간 검증이 불가능해진다.
5. **여러 사람의 답을 한 문장에 섞지 않는다.** 하나의 `text`에는 primary의 답이 근거로 있어야 하고, supporting은 보강일 뿐이다.
6. **없는 사람을 만들지 않는다.** 묶음이 애매하면 페르소나 수를 줄인다. 채워야 할 개수 같은 건 없다.

## 4. 출력

- 저장 위치: Firestore `projects/<pid>/personas/{id}` — `persona.schema.json` 준수. v0.3부터 repo에는 페르소나가 저장되지 않는다.
- `id`는 소문자·숫자·하이픈(예: `p-jiyeon`). 재생성 시 **같은 id를 유지**하고 `version`을 올린다.
- 갱신할 때는 `revisionNote`에 무엇이 왜 바뀌었는지 남긴다(어떤 서베이가 추가돼 어떤 특성이 바뀌었는지, primary가 교체됐다면 그 사실도). repo에 데이터가 없어 git diff로는 추적되지 않는다 — 이 필드가 유일한 변경 이력이다(ARCHITECTURE.md §2·§5).
- `generatedBy`에 모델 id, `createdAt`에 생성일.

**저장 전 자기 점검**

- [ ] 모든 `evidence[]` 항목에 `respondentLabel`이 있는가
- [ ] `answerProfile.respondentLabel`이 `sourceRespondents`의 `primary`와 같은가
- [ ] `evidence`의 `questionId`가 서베이 정의에 실제로 있는가 (`<qid>-c` 포함)
- [ ] `quote`가 원문 그대로인가 (요약된 문장이 섞이지 않았는가)
- [ ] `behaviorModel`의 각 항목이 특정 응답에 걸려 있는가 — 근거 없이 그럴듯한 항목이 없는가
- [ ] `demographics`에 응답에 없는 값이 들어가지 않았는가
- [ ] `contradictions`를 찾아봤는가 (없으면 "없음"이 아니라 정말 없는지 확인)

## 5. 실행 · 비용

- **모델**: Google **Gemini 2.5 Flash**를 Agent Platform(구 Vertex AI)에서 호출한다. 이 모듈은 텍스트 전용이고 실시간 응답이 필요 없으므로 **배치 모드**를 쓴다 — 표준가의 **50%**다. SDK는 `google-genai`, `enterprise=True`, 인증은 API 키가 아니라 ADC(`gcloud auth application-default login`). 근거와 단가표는 [docs/AI-PROVIDER.md](../../docs/AI-PROVIDER.md).
- **모델 호출부는 한 곳에 모으고, 모델명·제공자는 설정으로 뺀다.** 프롬프트 조립과 모델 호출을 섞지 않는다 — 나중에 모델을 바꾸거나 페르소나 품질을 A/B로 비교할 때 호출부 한 곳만 고치면 되게 한다.
- **로컬 실행 권장.** Actions에서 Firestore에 쓰려면 Firebase 서비스 계정(Admin SDK) 키를 repo Secrets에 등록해야 한다(ARCHITECTURE.md §7 — 미구현). 로컬에서 돌려 결과 JSON을 만들고 웹 페르소나 화면에서 넣으면 서비스 계정 키를 만들 필요가 없다. 초기에는 이쪽이 안전하다.
- **모델 호출 비용은 실행 전에 고지한다**(CLAUDE.md §3). 응답자 전원의 답변 전체를 컨텍스트에 넣으므로 **비용은 응답자 수에 비례**한다. 40문항 × 35명 규모면 배치 모드 기준 **회당 $0.05 안팎으로 추정**되고(표준 모드면 그 두 배), 응답자가 늘면 그만큼 늘어난다. **실측이 아니라 단가 × 예상 토큰 수 계산이다** — 단가가 낮아졌다고 고지를 생략하지 않는다.
- 비용을 줄이려면 응답자 수가 아니라 **서베이 단위로 나눠** 실행한다. 문항을 잘라내는 방식은 쓰지 않는다 — 프로필이 조각나면 이 모듈의 전제가 무너진다.

## 6. 입력 준비

서베이 결과 화면(M03)의 **응답자별 보기**에서 내보낸 파일을 그대로 입력으로 쓴다. 별도 변환이 필요 없다.

1. 서베이 결과 화면을 연다 → 상단에서 **응답자별** 보기로 전환 (`&by=respondent`)
2. 응답자 카드를 한둘 열어 프로필이 제대로 펼쳐지는지 눈으로 확인한다 — 라벨(`P7` 또는 `응답 #3`), 무응답 표시, 자유 의견
3. 목록의 **`전체 프로필 JSON`** → `<sid>-profiles.json` (응답자 전원)
   특정 한 명만 다룰 때는 상세 화면의 **`응답 프로필 JSON`** → `<sid>-<라벨>-profile.json` (단일 `answerProfile`)
4. (권장) 문항별 보기의 **`집계 JSON 내보내기`** → `<sid>.json` — 문항 정의와 집계(§1 보조 입력)
5. 두 파일을 에이전트에 넘긴다

내보낸 파일에는 응답 원문이 들어 있다. **repo에 커밋하지 않는다**(CLAUDE.md §2). 작업이 끝나면 로컬에서 지운다.

문항에 `personaDimension`이 태깅돼 있으면 단계 2의 묶음 기준이 훨씬 정확해진다. 연동 직후 태깅을 먼저 끝내는 것을 권장한다(docs/SURVEY-INTEGRATION.md).
